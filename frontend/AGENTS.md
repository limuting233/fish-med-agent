# 前端 Agent 协作指南

## 职责范围

本 Agent 在这个项目中专门负责 `frontend/` 工作区。

主要职责：

- 维护 Vue 3 + Vite + TypeScript 前端应用。
- 实现产品界面、交互状态、路由行为、前端状态管理和接口类型。
- 保持所有界面与 `frontend/DESIGN.md` 的设计方向一致。
- 在条件允许时，通过类型检查、生产构建和浏览器检查验证改动。

默认不要修改后端代码。只有当前端无法完成接口对齐时，才允许做非常小的后端契约确认或适配；如果后端接口已经变化，应先阅读后端 schema 或 endpoint 实现，再更新前端类型和映射逻辑。

## 项目背景

Fish Med Agent 前端承载以下用户流程：

- 登录与认证路由跳转
- 历史对话列表与搜索
- 聊天输入、消息流式响应和会话状态
- 图片/文件附件准备
- 鱼病诊断结果展示
- 用户账号信息展示

当前技术栈：

- Vue 3，使用 `<script setup lang="ts">`
- Vite
- TypeScript
- Pinia
- Vue Router
- Tailwind CSS v4 入口文件与组件内 scoped CSS
- `lucide-vue-next` 图标
- `vue-sonner` 通知组件

## 设计基准

做任何 UI、布局、样式或视觉细化前，必须先阅读 `frontend/DESIGN.md`。

`frontend/DESIGN.md` 是以下决策的主要依据：

- 视觉语气与产品氛围
- 字体、间距、圆角、颜色和层级
- 组件样式与交互状态
- 桌面端与移动端响应式行为

当前产品方向应保持克制、安静、专注于工作流。不要加入会抢走用户注意力的装饰性视觉。侧边栏、聊天区、表单、弹窗和输入框应像同一套产品系统，而不是彼此割裂的视觉实验。

## UI 原则

- 优先构建真实可用的产品界面，而不是营销页或占位演示。
- 登录页、侧边栏、聊天区、搜索弹窗、输入框等重复模式要保持一致。
- 图标按钮优先使用 `lucide-vue-next`，不要手写已有图标。
- 卡片圆角通常控制在 8px 以内，除非当前局部组件已有明确更大圆角模式。
- 避免卡片套卡片、重阴影和过度装饰。
- 不添加装饰性的渐变光斑、散景、任意插画或无业务意义的视觉元素。
- 桌面和移动端都要保证文字不重叠、不溢出、不遮挡交互目标。
- 对侧边栏条目、用户信息面板、按钮和紧凑控件设置稳定尺寸、截断和响应式约束。
- 空状态、加载态、错误态、禁用态、选中态、悬停态和聚焦态都要有明确设计。

## 组件与状态

- 组件职责要单一，命名要能表达用途。
- 抽取组件时，props 和 emits 要显式、可读、类型准确。
- 不为了“看起来抽象”而抽象；只有能减少重复或明确边界时才抽组件。
- API 响应类型放在 `src/api/*`，并尽量贴近后端契约。
- 认证、token、用户资料等状态放在 `src/stores/auth.ts`。
- 展示用派生文案可以放在渲染它的 view 或组件中。
- 不要把请求细节直接混进模板。

## 接口契约对齐

后端接口变化时，按这个顺序处理：

1. 阅读后端 schema 或 endpoint 实现，确认真实返回结构。
2. 更新对应的前端 API 类型。
3. 更新 store 或 view 中的字段映射。
4. 如果后端返回 snake_case，API 类型保留 snake_case；只有进入前端专用状态时才按需要转成 camelCase。
5. 运行前端构建和类型检查。

不要凭记忆猜接口字段。

## 样式规范

- 优先复用当前 view 或组件已有 CSS 变量，再考虑新增 token。
- 除非需要全局 reset 或应用级规则，否则样式保持 scoped。
- 复用已有间距、边框、圆角、颜色和文字层级。
- 优先用间距、细边框或背景差异表达分组，少用大面积卡片和重阴影。
- Fish Med Agent 的强调色优先使用 `var(--ocean-blue)` 及其相关局部 token。
- 移动端抽屉、侧边栏、弹窗和输入区需要主动设计，不能依赖偶然换行。

## 可访问性

- 尽量使用语义化 HTML。
- 图标按钮必须有清晰文本或 `aria-label`。
- 输入框必须有 label 或可访问名称。
- 键盘聚焦态必须可见。
- 不只依赖颜色表达状态。
- 装饰性图片和图标使用 `aria-hidden="true"` 或空 `alt`。

## 验证要求

代码改动后，根据改动范围运行相关检查：

- `npm run build`：类型检查和生产构建。
- 如果本地 dev server 可用，使用 `http://localhost:5173/` 做浏览器检查。
- 涉及布局时，检查桌面端和移动端，尤其是侧边栏、弹窗、输入区和新改动区域。

如果浏览器验证被登录态、缺少账号或环境限制阻断，需要明确说明，并至少完成构建验证。

## 工作方式

- 改动前先阅读相关本地文件。
- 改动范围保持聚焦，只处理当前用户请求。
- 不回退用户或其他工具做出的无关修改。
- 手动编辑文件使用 `apply_patch`。
- 搜索文件和内容优先使用 `rg` 或 `rg --files`。
- 最终回复要简洁说明改了什么、涉及哪些文件、验证是否通过。
